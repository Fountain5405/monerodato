## What this is

A fork of the FCMP++ stressnet monerod (seraphis-migration/monero) carrying optimisations for hardware that
cannot run the reference build: lower-memory proof verification, faster Field25519 arithmetic, merged batch
verifiers, and a startup read of the node's hash indexes for slow disks. It also changes the wallet's FCMP++ prover,
which builds transactions faster and with less memory. Same chain, same consensus rules as the reference build.
Every optimisation is compiled in and always on; there are no runtime switches, and the binary does not fall back
to the reference code on capable hardware. Instead, on a machine with at least 12 GB of RAM, 5 physical cores and
AVX2, it prints a notice at startup that the reference monerod can run there. If anything goes wrong, the fallback
is the stock binary on the same database.

## Testnet only

monerod, the wallets and the blockchain utilities start only on testnet, which is where the FCMP++ stressnet runs:
pass `--testnet`, or set `testnet=1` in the config file. On mainnet, stagenet or regtest they print one line and
exit before writing anything to disk. There is no flag, environment variable or config option that turns the check
off.

- **Why:** this is a build of a Monero beta, tested only on the stressnet. The reference beta defaults to mainnet,
  and on a mainnet data directory it would likely convert the database and then fail to follow the chain. That is
  from reading the code; it was not tried.
- **For mainnet or stagenet,** use the reference Monero software.
- **Details,** including the four small tools that have no check and what a test build is:
  [MONERODATO.md](https://github.com/Fountain5405/monerodato/blob/monerodato-v0/MONERODATO.md#testnet-only).

## Slow disks

Measured, not human-verified. Two sets of changes are for nodes on a spinning disk. Both work on the kernel's page
cache, not on the node's own memory.

- **The index warm-up (.5 to .7):** at start-up, a background thread reads the three hash indexes that every block
  looks up (key images, transaction hashes, block hashes) into the page cache, in file order, if they fit in 60% of
  the memory the node may use. On a spinning disk each lookup that misses the cache is a seek; read in file order,
  the 829 MB of indexes took 61 s on the test VM's 5,400 rpm disk, against 2,054 s in key order.
- **The cache drop and the pruning prefetch (.8, opt-in with `--db-cache-drop`):** each commit drops from the page
  cache the pages that earlier commits freed and the large transaction values they wrote once, so that the index
  pages stay cached when the database is larger than memory. Before each pruning step the node asks the disk for the
  pages pruning is about to read. Without the option, .8 behaves exactly as .7.

**The whole .9 against the reference build.** A 7,000-block sync onto a pruned database (3,106,401–3,113,400) from
one LAN peer, on a VM with 4 vCPUs, 4 GB of RAM and a 5,400 rpm disk, from a dropped page cache, 2 runs a side. The
1,536 MB cgroup cap stands in for a chain larger than the machine's memory. Every figure has disjoint ranges:

## Building

There are no binaries. To build the release on Ubuntu 24.04 (x86-64):

```sh
sudo apt update && sudo apt install -y build-essential cmake ninja-build pkg-config git curl
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y --profile minimal --default-toolchain 1.99.1
. "$HOME/.cargo/env"
git clone https://github.com/Fountain5405/monerodato.git && cd monerodato
git checkout v0.19.0.0-beta.3.1-monerodato.7
git submodule update --init --recursive
make -C contrib/depends HOST=x86_64-linux-gnu -j"$(nproc)"
cmake -G Ninja -S . -B build/static \
  -DCMAKE_TOOLCHAIN_FILE="$PWD/contrib/depends/x86_64-linux-gnu/share/toolchain.cmake" \
  -DCMAKE_BUILD_TYPE=Release -DARCH=default -DSTATIC=ON -DBUILD_TESTS=OFF
ninja -C build/static daemon
build/static/bin/monerod --version
```

For the wallets, add their targets: `ninja -C build/static daemon simplewallet wallet_rpc_server`.

**Tested with monerodato.7** on 2026-11-11: these commands with the two wallet targets and `-j4`, in a fresh Ubuntu
24.04 container with 8 cores and 6 GiB of memory, cloning this repository afresh and without credentials. The three
programs built in 6 min 46 s in all, package installation included, and reported
`v0.19.0.0-beta.3.1-monerodato.7-release`.

**Memory and time,** measured on 2026-11-09 with the working build monerodato.2 and the daemon target only, in fresh
Ubuntu 24.04 containers on a Ryzen 9 9900X. Slower CPUs will take longer.

| Cores | Memory | `ninja` jobs | Result |
|---|---|---|---|
| 8 | 6 GiB, plus swap | default (10) | built in 4 min 51 s in all; it used up to 6.3 GB of RAM and 2.8 GB of swap |
| 2 | 4 GiB, no swap | default (3) | ran out of memory near the end of the main build (step 260 of 283) |
| 2 | 4 GiB, no swap | `-j2` | built in about 9 min in all (timed in two parts); peak memory 4.07 GB, just under the limit |

- **With 4 GB of memory:** use `ninja -C build/static -j2 daemon`, and close other programs or add swap. `-j1` should need
  less, but was not measured.
- **What was checked on the monerodato.7 build:** each of the three programs refused to start on mainnet and on
  stagenet, and monerod on regtest, with nothing written to disk; with `--testnet` they started. The release's own
  checks are in [VERIFICATION.md](VERIFICATION.md).
- **Running it on another machine:** the binary links only glibc dynamically, and needs glibc 2.38 or newer (Ubuntu
  24.04, Debian 13 and later). Built on Ubuntu 24.04, it will not run on Ubuntu 22.04 or Debian 12.
- **Hashes:** builds are repeatable, not bit-for-bit reproducible, so your binary's sha256 will not match anyone
  else's. The binary also holds the path of the directory it was built in.
- **Network:** the `contrib/depends` step downloads the C and C++ libraries' sources. The Rust code builds offline from
  the vendored crates.
- **Not tested:** other distributions, ARM, and building without `contrib/depends`.

## How it is made

Developed and maintained by coding agents under human direction, in the lab behind the
[stressnet monitor](https://github.com/Fountain5405/stressnetmonitor). The release had to pass a differential
testing gate against the reference binary: fuzzing of each changed primitive, a corpus of transactions that both
binaries must reject or accept identically, and a replay of the same chain through both binaries with identical
verdicts and tip hash. The checks and their evidence are listed in [VERIFICATION.md](VERIFICATION.md). A human
decided that the release is tagged, but no human has verified that the optimisations are correct.

## Tested against known counterfeiting bugs

Rucknium's [2026 Counterfeiting vulnerabilities in cryptocurrency privacy projects](https://gist.github.com/Rucknium/a38821f8a1e0e0a115c0f4bc72d3bdb1)
describes eight bugs of 2026 that let someone create coins in other privacy projects. The adversary turned each kind
into tests against monerodato, ran them on .7 and on the prototype of .9's range-proof split, and reran on .9 the kinds
that the adopted gate tests cover. **No counterfeiting-class flaw was found.** That is a result of these tests, not a
proof; no human has reviewed them.

| Class | The bug elsewhere | Tested on | Result | What was tested in monerodato |
|---|---|---|---|---|
| C1 | Beam: transcript malleability | .7, prototype, .9 | every mutant rejected | range proofs permuted, omitted or spliced at every position, and at every batch split |
| C2 | Firo: transactions with several inputs | .7, prototype, .9 | verdicts identical to stock's | 396 structured mutants of real multi-input transactions, checked live against stock |
| C3 | Iron Fish: position in the tree | .7, prototype | all rejected | membership proofs with the input block swapped, the path cut short, or the root or signed hash replaced |
| C4 | Liquid: range-proof code | .7, prototype, .9 | as C1 | covered by C1's enumeration at the batch-split thresholds |
| C5 | Litecoin MWEB: pool and block disagree | .7, prototype, .9 | the block path checks first and refuses; the corrected block is accepted | mined blocks carrying transactions the pool stored without full checks, or never saw |
| C6 | Pirate Chain: block and wire disagree | .7, prototype, .9 | the block parses and is refused at verification | encoding mutants, and serialized blocks with one bit flipped in a transaction-hash entry |
| C7 | Zano: the transparent supply | .7, prototype, .9 | refused at the coinbase/reward check | coinbases that mint too much or claim too much fee, inside blocks with valid proof of work |
| C8 | Zcash: an optimisation gone wrong | .7, prototype | a valid re-mined transaction hits the cache; a broken one on the same ring is fully verified and refused | the verification cache across a reorganisation |

- **Not rerun on .9:** C3, because its test vectors predate .9's transcript change, which has its own corruption
  checks; and C8, because .9 does not touch the cache it tests.
- **The record and the data:** the [VERIFICATION.md section](VERIFICATION.md#the-2026-counterfeiting-survey-class-by-class-adversary),
  the adversary's [report](evidence/monerodato.9/adversary/adversary/survey-parity/report.md) with the raw run logs, and its
  [corpus tools](evidence/monerodato.9/adversary/tools/) and [method notes](evidence/monerodato.9/adversary/methods/).
- **The test code and how to run it:** [RUN.md](evidence/monerodato.9/adversary/adversary/survey-parity/RUN.md) gives, for each class, where its code is, the build, the
  command and the expected output. The C3 test, C8's reorganisation test and C6's serialized-route tests are in
  [tests/](evidence/monerodato.9/adversary/adversary/survey-parity/tests/), with [the lines that register them](evidence/monerodato.9/adversary/adversary/survey-parity/register.diff). C1, C4, C5, C7 and C6's bit flips are
  monerodato's own gate tests, which become public with the .9 tag. C2 runs on the corpus [tools](evidence/monerodato.9/adversary/tools/).
