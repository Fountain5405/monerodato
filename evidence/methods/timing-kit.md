# Method: the timing kit (resync from a fixed database, arms alternated)

**Run by:** coordinator. **Used for:** the CPU and wall-time claims of .9 on the Core 2 Quad and the Pentium G6950
(HDD) boxes. The HDD-VM kits behind the .8 HDD claims use a different method: see the optimizer's
[METHODS.md](../monerodato.9/METHODS.md). **Data:** `evidence/monerodato.9/data/perf/`. **Scripts:**
`evidence/tools/timing-kit/`.

## Question it answers

Does a candidate build (arm N) process the same stretch of real stressnet blocks faster than the baseline (arm B, or
the prototype P) on the same machine, by more than run-to-run noise?

## Fixed inputs

- **Database:** one LMDB copy of the stressnet chain, popped back to height 3,102,000. sha256 of `data.mdb`:
  `16c687f9f27b791e3414c0303603480c5a85c80b465e6d5af0a81cc7d974fbfe`. Every run starts from a fresh copy of it,
  checked against that sha256 before monerod starts.
- **Blocks:** the node fetches blocks 3,102,000 onward from the network as a normal sync. The blocks are the same in
  every run (the chain is final there). The peers are fixed too: on both boxes the unit has two `--add-exclusive-node`
  entries, the same two nodes on the same LAN, both synced to the tip. So the box never talks to any other peer. The
  order in which blocks arrive, and which of the two peers serves each batch, can still vary from run to run.
- **Binaries:** each arm is one monerod binary, identified by its sha256 (in each run's `driver.log` and the data
  README). The arm is switched by a symlink only; the systemd unit and its flags stay unchanged between runs.
- **Machine:** the same box for all runs of a kit, otherwise idle. Its normal monerod is stopped for the kit and its
  tip database is set aside, then restored at the end.

## One run

1. Copy the database to the data directory and check its sha256.
2. Point the binary symlink at the arm, start monerod with the box's normal unit, wait for RPC.
3. Start the sampler (5 s): monerod's `/proc/<pid>/stat` and `status` (CPU ticks, RssAnon, VmSwap), the host's
   `/proc/stat` and pressure (PSI) files, and the monerod log's per-block lines.
4. Every 5 minutes: CPU clock, load, thermal-throttle counters (`runN-A.clock.txt`). Per-thread CPU every 5 s
   (`thrstat.txt`, later runs; earlier runs used `pidstat`).
5. Stop rule: when the log's `Height:` line passes 3,103,452, which monerod prints for block 3,103,451 (monerod prints
   `Height: N` for block N-1). Read the node's CPU ticks and RssAnon at that moment.
6. Check correctness of the end state: the top block's hash against the reference node's at the same height, and
   count log lines matching `Failed to verify|verification failed|Maximum packet size` (expect 0).
7. Later drivers: wait 60 s, stop monerod, stop the sampler 90 s later, so the last samples are kept.

## Order

Arms alternate as B N N B (or P N N P), so a slow drift over the hours (page cache, disk state, temperature) affects
both arms equally. One box got an extra N B pair afterwards.

## Measures

- **Wall:** monerod start to the moment block 3,103,451 is added (from the log time).
- **Sum of p/t:** monerod's `block_processing_time` per block, from its log line `Height: N … p/t: T (…)ms`: wall
  time in `Blockchain::handle_block_to_main_chain` up to, not including, the database write. Summed over blocks
  3,102,001-3,103,451 (exact definition: the optimizer's [METHODS.md](../monerodato.9/METHODS.md)).
- **Node CPU:** utime + stime of monerod at the stop reading.
- **Scored range:** the optimizer's figures use blocks 3,103,300-3,103,450 (the heavy FCMP++ blocks); see the
  optimizer's [METHODS.md](../monerodato.9/METHODS.md).
- **Noise:** the spread between runs of the same arm in the same kit. A difference smaller than that spread is reported
  as no difference.

## What it does not show

- It does not check that blocks were verified *correctly*; that is the differential corpus and the gate tests. It only
  checks that the run ended on the same chain as the reference node, with no verification-failure lines.
- One box per kit, a few runs per arm: it detects differences larger than the run-to-run spread (measured 0.25-7 %
  on these boxes), not smaller ones.
- Network fetch time is inside the wall figure; the sum of p/t is the figure less affected by it.
