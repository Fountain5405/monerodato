Fork-gate design, all five sections. G009 and phase 4 are done, so this completes my queue. — adversary

1. REJECTION CORPUS
Build: a generator over real stressnet transactions (from blocks, all input-count shapes 1..128) plus the tests/data vectors, applying mutation operators: single/multi-byte flips per region (SAL section, FCMP body, root_blind_pok), cross-transaction splices, statement mismatches (wrong root / layers / key images / input reorder), shape lies (inputs/layers counts that mismatch the proof), and encoding edges (non-canonical field patterns in pseudo_outs / key images — p, p+1, 2^256-1 limbs). Oracle FIRST: every case is run against the reference binary; the corpus keeps (bytes, expected verdict, expected reason-CLASS) — parse-error / verify-fail / policy — never raw strings, since text drifts between versions. Two sets: REJECT (reference rejects; target ~5-10k to start) and MUST-ACCEPT (~500: unmodified real txs plus fee-tier edges). Growth: +500/week sampled from live chain txs so the corpus drifts with the network; every field-discovered bug becomes a locked regression case. Determinism: no timestamps or addresses inside cases; manifest with per-set sha256.
Needs from you: the LAN node with unrestricted RPC running BOTH binaries (or two nodes), a corpus directory, and a submit-rate cap (~10 req/s with do_not_relay) so the gate never load-tests your box by accident.

2. PRIMITIVE FUZZ (per primitive, crate-level model-vs-implementation, seeded and re-runnable as in-tree tests)
- Field backend (s64 or successor): boundary cross-product ops, wide_reduce limb extremes, from_repr acceptance sweep, eq-across-representations, hard functions on squares/non-squares/zero, overflow checks ON. Bar: 0 mismatches on >=5k structured + >=1M random ops.
- Batch merge/split (G009 or successor): merged-vs-per-batch verdict equivalence with malleated members, merge-order independence, every-field corruption propagation, empty-verifier padding, split engagement on >=2,048-term lists, and the null-state rule baked into the oracle (any failed batch => false). My three harness artifacts from the G009 review are documented traps: encode the null-state rule, corrupt in-range (the h_sum zip truncation), and keep full output captures.
- Transcript machinery (any folded-verify change): replay/state-equality fuzz, skip-lands-where-verify-lands.
- FFI wrappers: prepare/finish/destroy on real vectors across success, malleated, per-proof-failure, and double-destroy paths.
Cadence: every primitive change, plus a nightly random soak.

3. REPLAY GATE (formalizing what you do by hand)
Fixed popped-DB snapshot (hash recorded), fixed peers (2 honest refs + 1 silent under-reporting peer to hold the wedge conditions), both binaries sync the same stretch; compare per-block verdicts and the final tip hash. Add: (a) INJECTED BAD BLOCKS — blocks containing corpus rejection cases, fed through the BLOCK path, not just RPC (pool verification bypasses batchVerifyFcmpPpProofs; the optimizer's correction showed the block path is where merged verification lives and was the least-tested); (b) REORG SCENARIOS — pop N blocks onto a competing branch containing a bad-tx block; the fork must reject exactly where the reference does; (c) a heavy-window pass (the 128-input stretch) since that is the regime the optimizations target; (d) a memory ceiling check — peak anon RSS under the low-spec budget with >=10% headroom and no swap, because that is the fork's reason to exist. A runner script takes (reference sha, fork sha, snapshot hash, corpus manifest) and emits the report; you run it per release candidate.

4. REVIEW CHECKLIST (what I want in a diff before ship)
Every changed file with a per-hunk rationale; perf and behavior changes never mixed in one commit. Rust crypto: bounds proofs in comments (the s64 style), CT claims plus how they were verified and the caveat that CT is per-compilation, layout assertions. C++: an ownership walk of every raw pointer across the FFI on all four paths (success / null / throw / false), thread-lifecycle arguments (who waits for what, the WaitGuard class of issue), and a written known-issues list with accepted-or-fixed status. Build provenance: exact toolchain and flags, Cargo.lock with path patches resolved to pinned hashes, binary sha256 in the release manifest. State explicitly what testing CANNOT reach — formal CT proofs, hardware SCA beyond branch structure, months-scale soak, eclipse/partition games — so "gated" does not oversell.

5. PASS/FAIL
A candidate passes iff ALL of: primitive fuzz 0 mismatches on the exact release source (re-run after any toolchain or flag change); corpus 100% verdict agreement on REJECT and MUST-ACCEPT (reason-class >=99%); replay identical verdicts and tip hash including injected-bad-block and reorg scenarios, memory within budget; checklist complete with the sha chain from source to binary. Severity split: any case where the FORK ACCEPTS what the reference REJECTS is a hard fail regardless of everything else (soundness); fork-rejects-valid is a fail but labeled liveness. The reference path ships in the same binary behind a config switch, the switch itself is tested, and a failed gate demotes to reference automatically. Attach the artifacts (corpus manifest, fuzz logs, replay report, review doc, all hashed) to the owner's signature so the signature covers evidence, not just a binary.
