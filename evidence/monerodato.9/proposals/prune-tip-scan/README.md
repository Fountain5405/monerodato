# Proposed by others: stop the pruning tip scan at the first entry still inside the tip

**The change:** commit `427968267` (2026-10-13, from the proposer's public fork; no upstream PR). It adds five lines, an `else { break; }`, to the tip pass of `BlockchainLMDB::prune_worker` (`src/blockchain_db/lmdb/db_lmdb.cpp`). After every block batch, a pruned node walks the `txs_prunable_tip` table from its first entry and prunes the entries that have left the tip (5,500 blocks). Without the change the walk never stops early, so every pass reads the whole table. With it, the walk stops at the first entry still inside the tip.

**Status:** measured; not included in monerodato: it has no measurable effect on a sync, and would need more testing to show one. The original work stays in its author's repository.

**Result:** correct, and each pruning pass is 58% shorter. Over a sync the pruning time falls 7.7% (about 9 s in about 1,500 s), and the sync's rate and CPU per block show no measurable change.

## Why the early stop is safe
The table's key is the transaction id, an integer that grows with each added transaction, so along the key order the block heights never fall. A pop deletes the popped transactions' tip entries, and a resumed prune re-adds entries under their transaction ids, so the order also holds after reorganisations and resumes. If the order were ever broken, the cost would be entries left unpruned (disk space), never wrong data. The runs below check the order on the databases themselves.
