# Methods: how each monerodato.8 and .9 performance figure was measured

**p/t and t3, as used throughout.**
- **p/t** is monerod's `block_processing_time`, in milliseconds, read from its own log line `Height: N … p/t: T (13 fields)ms` (category `blockchain`, level INFO; `Height: N` means block N−1 was just added).
  - It is the wall time inside `Blockchain::handle_block_to_main_chain`, from entry (including the wait for the blockchain lock) through the proof-of-work and transaction checks.
  - It stops before the block is written to the database. That write is timed separately, in the line's last two fields (`addblock`, `advance_tree`).
  - When the proof of work was precomputed, its time is added.
- **t3,** the fifth of the 13 fields, is the part of p/t that checks the block's transactions: the FCMP++ tree root, the key images, and the batched proof verification.
- **The headline figures don't use either.** Wall time comes from the log's block times, and CPU from `/proc` samples. p/t and t3 appear only as per-block medians and sums.

Every measurement here followed the same rules.
- **Fixed in writing first:** the arms, the block range, the metric, a prediction with a range, and what each outcome would mean. All of this was written down and committed before the first run.
- **Alternating order:** the arms ran in alternating order (B N N B, or rounds whose order reverses), so a drift over the session hits both arms alike.
- **Same start for every run:** each run started from a fresh copy of the same database snapshot, on an otherwise idle machine, with the page cache dropped where the method says so.
- **Medians, not means:** each arm is summarised by the median of its runs, and a comparison is the ratio of the two medians.
- **The spread is part of the result.** "No overlap" means the arms' ranges are disjoint: the new arm's slowest run beat the old arm's fastest. Where the ranges overlap, the difference is within run-to-run noise and is reported as such.
- **Correctness was checked on every run:** each ended with the same block hash as a reference node at the same height, with no verification failures and no ERROR lines in the node log. A run that failed this would have stopped the release. None did.
- **Missed predictions are reported with the number.** They did not change what was published, except where a reading fixed in advance said so; those cases are noted below.

## monerodato.9

**What changed:** a block's range-proof (BP+) batch, its sum checks and its key-image domain checks used to run on one thread while the other cores waited. .9 splits them over the compute pool. The BP+ batch is split into at most one sub-batch per physical core.

### Replay on the 3900X and the 5600G
- **Metric:** wall time from block 3,103,320 being added to block 3,103,500 being added, from the node's own time-stats lines. Node CPU is user+system over the same interval, from 1 s samples of `/proc/<pid>/stat`, interpolated at both ends. The blocks are about 1,300 one-input FCMP++ transactions each.
- **Setup:**
  - Each run starts from the same database at height 3,103,300 and syncs from a stock node on the same LAN, which has the chain.
  - Governor `performance` during the run.
  - On the 3900X, the test node ran on 11 of the 12 cores (`taskset`) and the source node on the 12th. In the 4-core runs, the test node ran on CPUs 0-3 with `--max-concurrency 4`.
  - On the 5600G, the source node was on another machine.
- **Order:**
  - 3900X, 11 cores: B N P P N B;
  - 3900X, 4 cores: B N N B;
  - 5600G: B N N B.
- **Noise:** each arm's two runs differed by 0.1-2.3% in wall time, and the arms never overlapped.
- **Predictions** (fixed before the runs):

  | box | wall, .9/.8 | CPU, .9/.8 | result |
  |---|---|---|---|
  | 3900X, 11 cores | at most 0.85 | at most 1.04 | 0.771 and 1.002; both met |
  | 3900X, 4 cores | at most 0.90 | within ±3% | 0.847 met; CPU 0.965, just outside on the favourable side |
  | 5600G | at most 0.85 | — | 0.746; met |

  - **How the bars were set:** from the prototype's earlier result on the 3900X, 0.796 against .7.
  - **Failure:** a wall ratio above the bar would have meant finding the cause before review. A CPU rise above 4% with no wall gain would have meant dropping the per-core cap.

## monerodato.8

**What changed:** `--db-cache-drop`, off by default. It drops pages that LMDB freed, and transaction data written once, from the page cache. Before each pruning step it also asks the OS for the pages the pruning will read.

### The HDD VM kits (v10-v13)
- **Metric:** the rate in blocks per second over the "heavy part": the last 6,000 of 7,000 heavy stressnet blocks synced onto a pruned database (3,107,401-3,113,400). It is the blocks over the sum of the six 1,000-block windows' seconds.
  - Reads are kB per block from the block layer.
  - Each run starts from the same pruned database at 3,106,400, with the page cache dropped.
- **Two levels:**
  - no cap;
  - a 1,536 MB cgroup memory cap, which stands in for a chain larger than RAM.
- **Order:** F N N F at each level, 2 rounds. The no-cap result of kit v12 was repeated (kit v12r, N F F N) and pooled, four runs a side.
- **Noise:**
  - no cap: about 1-2% between rounds, but single runs of 5.50 and 5.49 occurred once in each arm;
  - under the cap: up to 9% between N's rounds in kit v10. That came from other lab traffic on the source.
- **Bars, fixed per kit:**
  - **E1:** under the cap, F's median rate at least 1.20x N's, and F's slowest run above N's fastest.
  - **E7:** without the cap, F at least 0.95x N.
  - **E10:** the binaries are the ones named.
- **Results:**
  - Kit v10 (cache drop alone) missed E7 at 0.89x. That is why the prefetch was added.
  - Kit v12 met every bar, and the repeat settled 0.96x against 1.02x as 0.99x pooled.
  - Kit v13 (the release against .7) met every bar: 3.69x and 0.98x.
- **Failure:** under 1.20x capped, or under 0.95x without a cap, would have kept the change out of the release. A hash mismatch would have stopped it.
