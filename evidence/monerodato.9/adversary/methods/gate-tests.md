# Method: the batch-verification gate tests

## What they prove

The fork verifies a block's range proofs, sum checks and key-image domain
checks in batches, split over a thread pool; a transaction arriving
through the pool is checked one at a time on the original code path. The
gate tests pin the equivalence: whatever one path rejects, the other must
reject, at every batch size where the splitting changes, with one defect
at every position. Batch verifiers in other projects have accepted bad
proofs that single checks reject; these tests are the tripwire for that
class here.

Three layers, all in the repository's test suite (test-only commits):

1. `tests/unit_tests/rct_batch_gates.cpp` (15 tests): batched BP+ and
   sum checks against single checks — a bad proof and a broken sum at
   every position of batches of 1..64, both verification entries; nine
   mutations of otherwise-valid proofs (swapped/reordered/truncated/
   duplicated/spliced fields); duplicated proofs; repeated-run verdict
   stability.
2. `tests/unit_tests/tx_batch_gates.cpp` (7 tests): transaction-level
   pool-vs-block equality — bad key image (a decodable point outside the
   prime-order subgroup), bad BP+ proof, broken balance, at 1..33
   transactions through the block-path batch entry; a position sweep at
   the split thresholds (17/33 transactions, defects at first/middle/
   last and across sub-batches); the input-verification-ID binding
   property; the output-type rules (hf16 today, hf17 pinned pre-activation).
3. The core-test families (22 instances; 25 with the wire-route bitflip
   instances): whole BLOCKS carrying one defective transaction — refused
   end to end, height unchanged, a corrected replacement accepted. Three
   delivery routes: pool-stored (kept-by-block) txs, a dishonest coinbase
   built into the block, and (the sync path) transactions delivered only
   with the block through a `supplemented_block` test event the pool
   never sees.

## Negative controls (the tests test something)

For each load-bearing check, a sabotage build must make the tests FAIL:

- Sabotage A — the sub-batch combination ignores failures of sub-batches
  other than the first: the bad-proof position tests in (1) fail.
- Sabotage B — `check_output_types` accepts an extra output type at hf16:
  `tx_batch_gates.output_type_rules` fails.
- Sabotage C — `ver_keyimages_domain_batch` returns true unconditionally:
  the bad-key-image tests in (2) fail.

Each control is one small local edit, rebuild, filter-run, revert; the
restoration run (clean tree) must pass everything again. The captured
outputs of the three sabotage runs and the restoration run are in
data/negative-controls/.

## How to rerun

From a test build of the repository:

    tests/unit_tests/unit_tests --gtest_filter='rct_batch_gates*:tx_batch_gates*'
    tests/core_tests/core_tests --generate_and_play_test_data --filter='gen_bad_*'

Expect 22 unit tests and 22 core instances (25 with the wire-route
family) all passing; about 70 s and 95 s respectively on a 12-core
desktop part. The sabotage controls: apply one of the three edits above,
rebuild, rerun the named filter, expect failures; revert.

## What they do NOT cover

- They pin verdict EQUALITY between paths and positions, not the
  soundness of the underlying cryptography.
- Verdicts are accept/reject; timing behavior is out of scope.
- The threshold constants (8 transactions, 16 signatures, 8 proofs per
  sub-batch) are pinned by the tests' size choices; a change to the
  constants moves which sizes matter, and the sweeps should be extended
  to bracket the new thresholds.
