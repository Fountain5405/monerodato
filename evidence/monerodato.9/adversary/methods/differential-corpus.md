# Method: the differential corpus (transaction-verdict equality between two nodes)

## What it tests

Two monerod nodes with different code are fed the SAME set of transactions
over RPC and must return the SAME accept/reject verdict on every one. Any
divergence means one node's consensus path disagrees with the other's on
the same input — the class of bug that has let forged value through in
other projects (a check present on one path and absent on another).

## Oracle setup

Two offline monerod instances on one host, each with its own data
directory copy of the SAME chain state, started with the same flags
(do-not-relay, offline). Each exposes its RPC over loopback only. The
runner (tools/fork_compare.py) holds one connection per node and submits
every case to both. A third comparison uses RECORDED verdicts taken in an
earlier run of the same case set against a reference binary: live-A vs
live-B, live-A vs recorded, live-B vs recorded. All three must agree.

The states sit either side of the heavy-block region used by the
performance experiments, so both the pre-FCMP and FCMP transaction mixes
are covered. The pool is empty at the start of every run and flushed
after any accepted case.

## Case sets

1. Accept parents (848 for H1, 50 for H2): real transactions exported
   from the chain below each anchor — the set every sane node must ACCEPT.
   A rejection here is a consensus break, not a mismatch.
2. Byte-flip mutants (2,000 per arm): one random byte XOR one random bit
   of an accept parent's serialized blob. Expected: reject on both nodes;
   the interesting failure mode is a mutant one node accepts.
3. Structured mutants (396, fork-format parents): eight classes over
   multi-input parents from the fork's own wire format — non-canonical
   (but value-preserving) varint re-encodings of the version and
   input-count fields, trailing and leading junk bytes, input-entry
   duplication, key-image copy, key-image swap, and a per-input amount+1
   claim tamper. These target the parser/wire and multi-input arithmetic
   surfaces specifically; the byte-flip set covers them only by accident.

## What counts as a match

Per case: verdict(stock) == verdict(fork), and, where a recorded verdict
exists, both live verdicts == recorded. A case accepted by either node
triggers a pool flush before the next case. Retry rules for transient RPC
failures (empty 200 bodies, connection drops) are in the tool; a case is
never silently skipped — after the retries it is recorded as failed.

## How to rerun it

See tools/README.md (entry-point commands). You need: two monerod
binaries, two chain data directories at the same height, and the case
files (or regenerate them with the tools from your own synced node at the
listed anchors). Per-case results for every run above are in data/*.csv
(case id, both verdicts, match).

## What it does NOT cover

- It compares nodes against each other and against recorded verdicts; it
  cannot find a bug that ALL compared binaries share.
- The case sets are transaction-level. Block-level divergence (a block
  accepted by one node and not the other) is covered by the gate tests in
  the repository's test suite, not by this corpus.
- Verdicts are accept/reject only; timing side channels are out of scope.
- The structured mutants are built from the fork's wire format; a future
  format change needs the generator rerun (tools/mutant_gen.py).
