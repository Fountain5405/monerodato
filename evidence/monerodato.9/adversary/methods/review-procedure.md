# Method: the second reviewer's release procedure

## Scope

Every release series in this repository (the .7 through .9 lineage and the
test-only gate series) goes through this review before the owner's go. The
reviewer is independent of the author: the author writes the series, the
reviewer reads it, reruns the evidence, and answers the author's questions;
the owner decides.

## Step by step

1. INTEGRITY: every artifact's sha256 is checked against the announcing
   letter. The bundle is fetched into a scratch clone and verified THIN
   against the stated base commit — the commit list must be exactly the
   announced one, and the total diff must touch only the announced files.
   Where a patch file accompanies the bundle, the delta it claims to
   represent is regenerated with git and compared byte-for-byte.
2. READING: every commit is read in full, diff first, then the surrounding
   code where the diff is not self-evident. The standing questions: what
   does a failure path degrade to (safe direction or not); what state
   survives an abort, a retry, a re-open; what is thread-owned and what
   is shared; which checks are equivalence-preserving reorderings and
   which change behavior. Claims in commit messages and docs are checked
   against the code — message-vs-code mismatches are recorded as defects
   even when the code is right.
3. LOCAL VERIFICATION: the series head is built in a scratch worktree
   (submodules initialized; -j2) and the relevant suites rerun — the
   project's own tests, the gate tests, and any family the series touches.
   Numbers reported by the author are reproduced, or the difference is
   chased (one memorable case was a missing test helper binary in a
   targeted build, not a code fault).
4. ADVERSARIAL LAYER: the differential corpus (see the corpus method) is
   run against the release binary on both chain anchors, plus the
   structured mutants. Live verdicts must match the stock baseline and the
   recorded labels on every case.
5. ANSWERS: the author's specific questions are answered with file:line
   evidence, not agreement. Where the answer is "cannot happen", the path
   is traced in source and quoted; where it is "possible but bounded",
   the bound is stated.
6. VERDICT: a letter to the coordinator states approve or not, every
   finding with its severity, and what was verified locally versus read
   only. Cosmetic findings are listed as pre-tag fixes. The verdict is a
   REVIEW STATEMENT, not evidence; the evidence is the rerunnable
   material in methods/ and data/.

## What this procedure does not do

- It does not re-derive the cryptography; it pins behavior (verdict
  equality, refusal provenance, refusal end-to-end).
- It does not fuzz; the fuzzing history and its surviving data are
  described in the vector-differential method note.
- It reads every line the series changes, but it cannot certify the
  unchanged ocean around it.
