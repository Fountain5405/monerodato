# Method: statement-level differential fuzzing (history and surviving data)

## What it was

Before the corpus existed, the FCMP++ verification layer was fuzzed at the
STATEMENT level: verified-input vectors (the repository's
`tests/data/fcmp_pp_verify_inputs_*.bin`) were mutated structurally and the
mutants were fed to two implementations of the verifier — a folded
single-statement path and a stored/batched path — plus the batch verifier,
with the internal verifier state inspected after each run. Any divergence
between the implementations' verdicts, any panic, and any acceptance of a
mutated statement were the failure bars.

- ~900 structured mutants over 15 mutation shapes and 7 strategies
  (bit flips in proof/SAL/key-image/pseudo-out/root/signable-hash regions,
  layer-count off-by-one, key-image swaps, multi-bit bursts).
- Result on the audited build: verdicts identical between all paths on
  every mutant; 0 panics; 0 acceptances of invalid statements.
- The harness lives in the monero-oxide tree the fork vendors
  (`differential_fuzz.rs`); the fork's crate retains
  `fuzz_test_arithmetic_circuit` with corruption checks at chosen proof
  positions, which runs as part of the crate's test suite with
  `--features tests`.

## What survives

- The mutation OPERATIONS are reproducible from the vendored
  `corpus_generator.py` (tools/): same seed discipline, deterministic case
  ids. The vector files are in the repository.
- Verdict TABLES for the runs against the audited build survive in the
  review evidence history; the per-mutant raw logs of the earliest runs do
  not all survive — the tables record per-case verdicts, not byte logs.
- The .9 series' transcript-skip change (VerifierTranscript::skip_point)
  added new corruption checks to the crate fuzz test; those run green in
  the release checks (see the repository's Checked list).

## How to rerun the surviving part

From the fcmp_pp_rust workspace of a test build:

    cargo test --features tests --release -p generalized-bulletproofs

and the vector mutations via tools/corpus_generator.py against a build
exposing the statement verifier (the unit-test harness
`fcmp_pp.cpp:batch_verify_from_file` is the entry that consumes the
vectors).

## What it does not cover

- Statement-level fuzzing predates the block-path batch changes of .9;
  those are covered by the gate tests and the differential corpus, not by
  this fuzz history.
- The earliest runs predate .8; their conclusions were carried forward
  only where the audited code was byte-identical, and that carry-forward
  is stated where used, not assumed.
