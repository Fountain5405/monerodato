# .8's disk commits against stock, on a slow disk (HDD VM)

**What this measures:** what monerodato.8's two disk changes bring against stock code on a slow disk:
- the LMDB page cache drop (monero 0012-0016, opt-in with `--db-cache-drop`);
- the pruning prefetch (monero 0017, which runs only while the cache drop is on).

**The base** is stock plus monero 0001, 0002 and 0004 (the memory fixes), the same for all three setups. Without the memory fixes, stock's memory under the cap would mix memory and disk effects.

**Result:**
- **Under a 1,536 MB cap,** the cache drop cuts launch to top by 35.4% (3,663 against 5,669 s), runs the heavy part 1.76x as fast, and reads 54% less a block.
- **Without a cap** it makes no measurable change.
- **The prefetch** adds nothing measurable on this base, with the cap or without it.

## Setup
- **Machine:** a VM with 4 vCPUs and 4 GB RAM, no swap, Linux 6.8, its disk on a 5,400 rpm HDD.
- **Builds:** three static release builds, made the same way (Release, `STATIC=ON`, default `ARCH`, `BUILD_TESTS=OFF`), from stock v0.19.0.0-beta.3.1:

| arm | code | started with | monerod sha256 |
|---|---|---|---|
| **B** | stock + monero 0001 `a8567e6ce`, 0002 `994918a78`, 0004 `412d6c9d3` | (nothing) | `9cbc14e01d66200744dedbb6b44f2bac3e1e551a6a77d14ed926e7e81cc3d4c9` |
| **C** | B + monero 0012-0016 (`aead98ebd`, `87f401be7`, `a3b780722`, `b3a2bf8c0`, `bd5c6b340`) | `--db-cache-drop` | `c42bb0716561ccd00c5167a8de9ba73022d267b692f60b07a482078e9b823d81` |
| **F** | C + monero 0017 `da1dcb451` | `--db-cache-drop` | `682824085782f6cedec79b3769ab058d26e348de817d2ad29c797277070c7170` |

- **The back-port.** 0012, 0013, 0015 and 0017 do not apply to stock as they are: their context includes .7's index warm-up, which stock lacks. The conflicts were context only. Each back-ported commit adds and removes exactly the lines of its .8 original.
- **The sync:** 7,000 blocks (3,106,401-3,113,400) onto a pruned stressnet (testnet) database, restored from the same snapshot before each run, from one LAN peer (`--add-exclusive-node`, written `<peer>` in the files).
- **Two stages:** without a memory cap, then under a 1,536 MB cgroup cap (`MemoryMax`, no swap). Each stage ran in the order B C F F C B, so each arm ran twice, in the first and the second half. Page cache dropped before each run; timeout 9,000 s.
- **Correctness:** every run's block hash at 3,113,400 was compared with the reference node's (`5a956cc4b1d1…`).

- **The figures:**
  - Each ratio is of the two arms' medians, which with two runs is their mean.
  - "No overlap" means both runs of one arm are on the same side of both runs of the other.
  - The heavy part is windows 2-7: 6,000 blocks over the sum of those windows' seconds.
- **Reads:** under the cap, the heavy part read 80 kB a block in C (79.8, 80.3) against 174 in B (172.7, 176.0).
- **Under the cap, C and F keep 95-97% of their uncapped rate, and B keeps 55%.** The cache drop recovers almost all of what the cap costs.
- **Every run** reached the top with the reference hash and 0 ERROR-level log lines. `LMDB page cache drop: on` was logged once in every C and F run and never in B. No run was OOM-killed or timed out.

**Why the sync runs at about 2 blocks a second** (the .8 release test ran .7 and .8 at about 5.8 on the same VM):
- this base has no index warm-up (.7 has one), so blocks 3,106,401-3,111,400 run on a cold index. They read 31-249 kB a block, where .7 and .8 read 0 after the first window.
- CPU per run is also about 31% higher than .7's (no verifier speed-ups), but the process averaged 1.3 cores, so the disk is the main limit.
- **This is also why the prefetch shows nothing here:** its reads in the last 2,000 blocks (97 and 135-139 kB a block) match what .8 read there, and the cold index reads before them are the same in all three arms.

## Files
- `data/stage/results.txt`: the driver's lines per run:
  - RESULT (outcome, launch to top, CPU, disk read and write, peak RssAnon, cgroup peak, OOM and refault counters, hash at 3,113,400);
  - IOSTAT;
  - WINDOW (7 windows of 1,000 blocks: seconds, blocks/s, read and write kB a block);
  - CACHEDROP (whether the node logged the cache drop line).
- `data/stage/log.txt`: the driver's log, with each binary's sha256 prefix and version. `stage1/`, `stage2/`: the driver's output per run.
- `data/runs/<start>-g019d-s<stage>-r<run>-<arm>/`: per run,
  - `summary.txt` (setup, cgroup state at the end, the RESULT and WINDOW lines);
  - `height.csv` (height over time);
  - `cgmem.csv` (cgroup memory over time, capped runs only);
  - `monerod.log` (the node's log at its default level).
- `scripts/score.py`: the scorer, standard library only. It reads the files above and recounts ERROR lines from each `monerod.log`.
