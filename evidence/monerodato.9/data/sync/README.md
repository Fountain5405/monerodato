# Whole syncs on two low-spec machines

These are the data behind the README's "On real low-spec machines" rows for the Atom N450 and the Pentium G6950.
Each run is a sync on the FCMP++ stressnet from a database popped to block 3,102,000 to the machine's catch-up
with the chain, one run per build, on the machine's own hard disk.

| Directory | Machine | Runs |
|---|---|---|
| `atom-n450/` | Atom N450, 1 core (2 threads), 1 GB RAM, 5,400 rpm hard disk | `stock` (11-08), `dot7` (11-11), `dot8` (11-15, started with `--db-cache-drop`) |
| `pentium-g6950/` | Pentium G6950, 2 cores, 3.7 GB RAM, hard disk | `stock` (11-12), `dot7` (11-12) |

## Files
- **`runs.csv`:** one line per run: name, start and end of its window (UTC epoch seconds). Each run is confined to its
  own window, so a later run on the same machine is never counted for an earlier one.
- **`blocks_<run>.csv.gz`:** `height`, `added_utc_epoch`: the first time the node added each block in that window,
  from its log (block N is the log's `Height: N+1`).
- **`procinfo_<run>.csv.gz`:** the node's process samples from the same monitor: `pid`, CPU seconds, anonymous memory
  (RssAnon) and swap, in bytes.
- **`../block_timestamps.csv.gz`:** each block's header timestamp, from a reference node, for the catch-up rule.
- **`compare.txt`:** the output of the command below.

## The rules, and the command
```sh
python3 -I scripts/sync_compare.py data/sync/atom-n450
python3 -I scripts/sync_compare.py data/sync/pentium-g6950
```
- **Stall:** a gap of 10 min or more between two consecutive recorded blocks across which the node was restarted (the
  process id before and after the gap differs). Every stall here is one that only an operator could end: the
  reference build's 100 MB message limit (both machines), and a peer that did not have the needed blocks (the
  G6950). Slow stretches where the node was busy with the CPU or the disk count as sync time.
- **Catch-up:** the first block from which the run receives blocks within 30 min of their timestamp.
- **Common range:** block 3,102,001 to the earliest catch-up of the runs, so that every run is compared over the same
  blocks. The later builds were still syncing there.
- **Memory:** the peak RssAnon, the peak swap and the peak of their sum, from the run's start to the end of the
  common range.

## Notes
- **One run per build** on each machine. On the Atom, .7 and .8 differ by 2.9%, which is within what one run each can
  show.
- **The G6950's reference run** was restarted twice to get past its stalls: once to add a second peer, and once to add
  `--block-sync-size 5` after the message limit. The script finds both from the process ids.
- **Twelve blocks are missing** from the G6950 reference run's records (3,105,394-3,105,405), at the end of its
  second stall. The node's chain has them; the monitor holds no add time for them. The totals are unaffected, and the
  gap is counted as a stall from block 3,105,393 to 3,105,406.
- **The Atom's .8 run** was started with `--db-cache-drop`.
