# FCMP++ proving time and wallet transaction-build time: data and methods

## Summary
monerodato's multiexp change, multiexp 0001 (`b8df9a72a`), makes the constant-time multiexp use Straus with a 4-bit window at every length. The FCMP++ prover spends most of its time in that multiexp.

Every figure below compares **multiexp 0.5.2** against **0.5.2 + that change**. 0.5.2 already has the constant-time Pippenger bucket fix, and it is what stock stressnet-v3 locks. **0.5.1, from before that fix, was never measured in these data.** A like-for-like run of 0.5.1, 0.5.2 and 0.5.2 + Straus(4) (single thread, 5 layers) is in progress, and its results will be added here.

**Prover only, seconds per membership proof** (`Fcmp::prove`, Ryzen 9 3900X; medians over the cases at each input count):

| inputs per proof | 1 | 2 | 8 | 32 | 128 |
|---|---|---|---|---|---|
| multiexp 0.5.2 | 0.71 s | 1.68 s | 8.69 s | 33.24 s | 155.29 s |
| 0.5.2 + Straus(4) | 0.50 s | 0.88 s | 3.59 s | 15.43 s | 70.96 s |
| change | −28% | −47% | −59% | −54% | −54% |

**What this table is, and is not:**
- **Indicative only.**
  - The cases ran **10 at a time** on a 12-core machine, one thread per case, so cases competed for caches and memory bandwidth.
  - Each input count **mixes tree depths from 1 to 8 layers**: 8 to 38 cases at each count.
  - It is not a single-thread, fixed-depth measurement. The run in progress is.
- **Correctness:** for all 258 cases, the two builds made byte-identical proofs, and the 0.5.2 build's verifier accepted the other build's proofs.

**Whole transaction in the wallet** (`monero-wallet-rpc` `sweep_all`, never relayed; medians of 3 rounds a side; every run with the change was faster than every run without):

| machine | 8 inputs | 32 inputs | 128 inputs |
|---|---|---|---|
| Ryzen 9 3900X, wall | −51% (6.35 → 3.11 s) | −51% (24.68 → 12.08 s) | −48% (100.83 → 52.09 s) |
| Ryzen 9 3900X, CPU | −45% (7.22 → 3.97 s) | −45% (28.26 → 15.56 s) | −42% (115.21 → 66.54 s) |
| Core 2 Quad Q6600, wall | −48% (37.14 → 19.20 s) | −57% (183.54 → 79.51 s) | not measured |
| Core 2 Quad Q6600, CPU | −46% (38.99 → 21.01 s) | −55% (190.84 → 86.78 s) | not measured |

- **One core:** the wallet's CPU time per wall second was 1.14-1.29 on the 3900X and 1.04-1.13 on the Q6600. The prover itself is single-threaded.
- A transaction has one membership proof covering all its inputs. The rest of the build is mostly the BP+ range proof (about 0.1 s at 1 input) and the wallet's own checks.

**The multiexp alone** (constant-time, Selene points, 3900X): Straus(4) took 43.6% less time than 0.5.2's own algorithm choice at 128 points, 68.9% less at 512 and 66.4% less at 2,048. Straus(4) was the fastest of every Straus window (2-6) and Pippenger window (2-8) at every length from 4 to 2,048.

## The arms
- **Wallet and prover data:**
  - the base is monerodato.2;
  - the other arm is monerodato.3, which is .2 plus multiexp 0001 (`3e1037de1` in the pre-publication history) and docs and build plumbing.
- **The .2 and .3 tags are in the pre-publication history, which is not public.** The public commit `b8df9a72a` is the same patch: `git patch-id --stable` gives `f7ed17a68258` for both.
- **The wallet memory steps** (`mem_f2.csv`) are .3, then .3 plus monero-oxide 0007 (`ed01fbd43`), then plus 0008 (`6c31ede43`), then plus 0009 (`2912fdd99`).
  - Each measured step has the same patch-id as the public commit.
  - The measured copies differ only in comments.
- **To rebuild both arms from public refs:** check out a public monerodato tag (for example `v0.19.0.0-beta.3.1-monerodato.9`). Build it once as it is (with the change) and once after `git revert b8df9a72a` (without it).
  - The base is then newer than .2, so the figures need not match exactly.
  - **Stale Rust library trap:** ninja does not re-run cargo when only files under `src/fcmp_pp/fcmp_pp_rust/patched/` change. Before the second build, delete `build/<dir>/src/fcmp_pp/fcmp_pp_rust/libfcmp_pp_rust.a`. Then check that the build log shows `Compiling multiexp` and that the binary's hash changed.

## Method: wallet transaction build
**What a run does:**
- a copy of a stressnet wallet;
- freeze every output, then thaw exactly n;
- `sweep_all` to the wallet's own address with `do_not_relay`;
- record the RPC's wall time and the `monero-wallet-rpc` process's CPU time (`utime + stime` from `/proc/<pid>/stat`) over that one call.

The built transaction is discarded. Fees and weights were identical between the arms.

**Needs:**
- a stressnet wallet with at least 128 unlocked outputs, **used only as a copy** (freezing is stored in the wallet file);
- a daemon synced to the chain the wallet knows. On the 3900X it was offline: `--offline`, no peers, on a copy of a synced database. On the Q6600 it was the local node;
- python3 and curl.

### 3900X (`wallet/3900x/`)
| file | what |
|---|---|
| `wprof_sync.sh` | brings a copy of a stressnet database to the tip from one peer, then stops |
| `wprof_up.sh` | starts the offline daemon on that database, and a wallet-rpc on the wallet copy |
| `wprof_drive.py` | the driver: `wprof_drive.py <wallet-rpc pid> <out.csv> <n,n,...> <rounds> [prep]`. `prep` freezes every output once. It thaws n outputs of one amount, oldest first; set `WAVE_AMOUNT` to an amount your wallet holds 128 or more of. Writes `utc,round,n_inputs,wall_s,cpu_s,cpu_per_wall,n_txs,fee,weight,tx_size_bytes` |
| `wprof_ab_dot3.sh` | the A/B as run: .2 and .3 native wallet-rpc, each on its own wallet copy, against the same daemon; 8, 32 and 128 inputs; 3 rounds, with the arm order alternating; governor `performance` |
| `memprobe.py`, `f2_chain.sh` | the wallet memory steps: a fresh wallet-rpc per arm and round, VmHWM after open and refresh, then after 8, 32 and 128 inputs; 3 rotated rounds. `f2_chain.sh` also built the step arms and ran a proof differential and the crate tests on the last step |

Builds were native: `cmake -G Ninja -D CMAKE_BUILD_TYPE=Release -D ARCH=native`, then `ninja wallet_rpc_server`.

### Q6600 (`wallet/q6600/`)
| file | what |
|---|---|
| `run_kit.sh` | the kit as run: two static wallet-rpc binaries, each on its own copy of a wallet copy, against a local daemon. Per round and arm: a 1-input warm-up (not counted), then 8 and 32 inputs; 3 rounds, arm order alternating. It refuses to run without `I_AM_A_COPY=yes` |
| `q6600_drive.py` | the driver: the same steps as `wprof_drive.py`, plus `subaddr_indices_all` and a check that the transaction spends exactly the n thawed key images. `do_not_relay` is hard-wired, and the script refuses relay methods. Writes `utc,arm,exe_sha,n_inputs,wall_s,cpu_s,cpu_per_wall,n_txs,fee,weight` |

Builds were static, generic x86-64: the depends toolchain, `-D ARCH=default -D STATIC=ON -D CMAKE_BUILD_TYPE=Release`, then `ninja wallet_rpc_server`.

The run: `I_AM_A_COPY=yes DAEMON=127.0.0.1:<rpc port> WALLET_DIR=<dir with a COPY> WALLET_NAME=<file> bash run_kit.sh`, with the two binaries named `monero-wallet-rpc-dot2` and `monero-wallet-rpc-dot3` next to it.

## Method: the prover
### Per-proof differential (`prover/differential/`)
- **What it is:**
  - a scratch copy of the prover crate (`full-chain-membership-proofs`);
  - a seeded RNG in place of `OsRng`, so a seed gives the same proof bytes;
  - an ignored test that builds the tree and blinds, times `Fcmp::prove` alone, writes the proof and verifies it (`harness.diff`).
- **Two arms**, built with `cargo test --release` and `--config patch.crates-io.multiexp.path=...`:
  - one with crates.io multiexp 0.5.2;
  - one with the patched multiexp.
- **`run_diff.py`** ran 258 cases: inputs 1-128, depths 1-8, two kinds of tree (`cases.txt`, named `inputs_layers_seed_kind`). It ran them in 10 shards at once, so **the times are indicative**.
- **The results:** `data/summary.txt` has the byte-identity and cross-verification results, and `data/prove_times.txt` the median per input count. `data/proof_sha256s.txt` lists each proof's hash.

### The multiexp micro-benchmark (`prover/mxbench/`)
- It needs a copy of crates.io multiexp 0.5.2 in `mxbench/multiexp/`, with `mod straus` and `mod pippenger` made `pub`, along with their `straus` and `pippenger` functions.
- Part 1 (`mxbench 1`) gives the constant-time time per length (4-2,048) for each algorithm and window, and for the crate's own choice (`auto`); the output is `data/mx.csv`.
- Part 2 (`mxbench 2`) splits Straus(4) over 1, 2 and 4 threads; the output is `data/mx2.csv`. That split is not in monerodato.
- `Cargo.toml` points at a monerodato tree's patched helioselene and dalek-ff-group and at its vendored crates; edit the paths.
